# Обмен ИИ ↔ конструктор Modulero

Черновик 0.1 от 2026-10-28. Основа — `main` репозитория `proc2010-Claude/modulero-next` на `cbaf1534`, каталог фурнитуры `hw-2026-10-27.8`. Решений владельца под это нет: всё ниже — предложение (Д), а не действующее правило. Определения инструментов — `examples/tools.claude-api.json` (сейчас их выполняет стенд по вызовам Claude в треде, позже — те же определения для Claude API).

## 0. Главный принцип

ИИ не считает. Размеры деталей, зазоры, фурнитура, допустимость, 3D и цена — только из движка Modulero. ИИ выбирает правки из закрытого списка, стенд (позже сервер) применяет их редактором ядра и возвращает результат или отказ словами движка. ИИ пересказывает ответ и задаёт следующий вопрос.

## 1. Что уже есть в Modulero (проверено по коду)

| Что | Где | Что это даёт ИИ-диалогу |
|---|---|---|
| Правки шкафа и купе — чистые функции `вход → { ok, input, notice } \| { ok: false, problem }` | `packages/core/src/wardrobe/editor.ts`, `fittings-edit.ts` | Готовый набор правок с проверкой и отказом по-русски: размер, секции, фасады, антресоль, основание, декор, наполнение, двери купе, помещение |
| Правки кухни — `KitchenEdit` той же формы | `kitchen/editor.ts`, `materials.ts`, `options.ts`, `obstacles.ts`, `module-fill.ts` | Помещение, тип, угол, остров, модули по 38 карточкам каталога + 2 доступных угла, положение и размеры, материалы, пометки стен, настройки кухни |

Чего нет: API команд правки на сервере (задача PLAT-9, перед первым релизом, MOD-DEC-498). Пока его нет, прототип ИИ-диалога работает на стенде, который вызывает ядро напрямую (`tools/kitchen-dialog-run.mts` — пример), а не на сайте.

## 2. Схема

### 2.1. Сейчас: стенд без API и без публикации

```
тред проекта: владелец пишет как человек ──► Claude в треде играет ИИ из диалога (SYSTEM_PROMPT_DRAFT.md)
                                                 │  вызов инструмента: npm run dialog -- kitchen_edits '<JSON>'
                                                 ▼
стенд modulero-ai ──► редактор ядра @modulero/core (modulero-next только для чтения, закреплённый SHA)
   │  ответ по §5: applied, refused, state, price, warnings
   ▼
sessions/<имя>/: файлы проекта версий, история, журнал, диалог + страница прототипа HTML
```

- Ключа Claude API нет; сервер и сайт Modulero не участвуют.
- Договор инструментов (§4, §5, `tools.claude-api.json`) тот же, что в схеме 2.2: стенд выполняет те же вызовы, которые потом будет делать модель через API.
- Страницу прототипа видит только владелец: файл в папке проекта или частная страница Artifact.

### 2.2. Позже: сайт и Claude API (после решения владельца и PLAT-9)

```
браузер: окно диалога + 3D-просмотр
   │  реплика человека, нажатая кнопка                   ▲ текст ИИ, кнопки, ссылка на 3D версии
   ▼                                                      │
сервер Modulero: оркестратор ИИ-диалога ───────────► Claude API (модель, системный промт, инструменты)
   │  вызов инструмента (kitchen_edits …)          ◄──── tool_use
   ▼
команды правки (PLAT-9) → редактор ядра @modulero/core → граф → сцена 3D, цена, замечания
```

- Ключ Claude API и движок — только на сервере. Браузер не говорит с Claude API напрямую.
- В Claude API уходят: системный промт, реплики человека, вызовы инструментов и их ответы. Ответы инструментов — в объёме экрана конструктора (MOD-DEC-497 §9 «Минимум в ответе»): без ставок, себестоимости, номеров правил и внутренних id каталога, кроме тех, что нужны для следующей правки.
- 3D браузер берёт по ссылке на версию (`/api/projects/:id/scene?rev=…` или сеанс без входа), а не через ИИ.

## 3. Сеанс, проект, версии

- **Сеанс диалога** — один разговор. Без входа живёт во вкладке, как проект редактора без входа (497). Сохранить проект — только с аккаунта, обычным сохранением конструктора.
- **Проект** — тот же объект, что у редактора: `WardrobeProject`, `KitchenProject` или `HomeProject`. `project_id` выдаёт сервер.
- **Версия** (`revision`) — после каждого успешного `*_edits`. Для кухни это `projectRevisionId` графа (`KPR2-…`), для шкафа — `MWD-…`. Каждый вызов правок передаёт `base_revision`; если проект изменили в редакторе в другой вкладке, ответ — отказ `STALE_REVISION` и текущее состояние.
- **История** — список версий с `label` каждой правки. `undo` возвращает к любой версии из истории, не стирая остальные.
- **Квоты** (Д): один вызов `*_edits` — одна правка в квоте 497, сколько бы правок ни было внутри (не больше 20). Квота на реплики ИИ нужна только после подключения Claude API (это расход, решает владелец; предложение на тот момент — 40 реплик в сутки без входа, 200 с аккаунтом). На стенде квот нет.


Правила ответа:

1. Правки выполняются по порядку. Первая отказанная останавливает остальные (`not_run`); проект остаётся в состоянии после последней принятой. ИИ видит отказ и решает: предложить другой вариант, спросить человека или повторить с другими числами.
2. `problem` и `notice` — слова движка, без изменений. ИИ пересказывает их проще, но не меняет смысл.
3. `state` — сводка в объёме экрана, без внутренних полей проекта. Полный `KitchenProject` или `WardrobeInput` в ИИ не уходит: они большие и раскрывают устройство.
4. `price` — то, что показывает полоса цены конструктора: сумма, округлённая до 10 ₽ (MOD-DEC-346, 538), статус, что не посчитано. `amount_rub: null` — цены нет, ИИ называет только известную часть и говорит, что она неполная.
5. Ошибка сервера — `{ "error": "…" }` с `is_error: true` в `tool_result`; ИИ извиняется одним предложением и предлагает повторить.

## 6. Пример: «Хочу кухню» (прогон на настоящем движке)

Ниже — разговор, правки которого выполнены настоящими функциями ядра на `main cbaf1534` (`tools/kitchen-dialog-run.mts`). Ответы движка, версии и суммы — из прогона (`examples/kitchen-dialog.log.json`), реплики человека и ИИ — образец. Файлы проекта после каждого шага — `examples/kitchen-step1…4.modulero`, они открываются `readProjectFile` как редактируемая кухня. Картинки — `examples/kitchen-step2…4.svg` и `kitchen-previews.png`.

**Ход 1.**
> **ИИ:** Какая мебель вам нужна?
>
> **Человек:** Хочу кухню.

ИИ сразу создаёт стартовую кухню и задаёт главные вопросы одним сообщением.

```json
{ "name": "start_project", "input": { "kind": "kitchen", "template": "empty" } }
```
Ответ: проект `p_7f3c`, версия `KPR2-a7eb341b4c337309`, помещение 3000 × 2600 × 2500 не подтверждено, модулей нет, цена 0 ₽.

> **ИИ:** Начнём. Расскажите три вещи: кухня вдоль одной стены, угловая или П-образная? Какой длины стены и какая высота потолка? Что из техники встраиваем: холодильник, духовку, посудомойку, стиральную машину?
>
> *(кнопки: Вдоль одной стены · Угловая · П-образная · Не знаю, помогите)*

**Ход 2.**
> **Человек:** Вдоль одной стены 3,2 метра, потолок 2,7. Холодильник встроенный, духовка под столешницей, мойка и посудомойка.

```json
{ "name": "kitchen_edits", "input": { "project_id": "p_7f3c", "base_revision": "KPR2-a7eb341b4c337309",
  "label": "Прямая кухня 3,2 м с техникой",
  "edits": [
    { "op": "set_room", "key": "width", "value": 3200 },
    { "op": "set_room", "key": "height", "value": 2700 },
    { "op": "set_type", "type": "straight" },
    { "op": "add_module", "card": "tall-fridge-one", "wall": "A", "pos": 0, "width": 600 },
    { "op": "add_module", "card": "lower-oven", "wall": "A", "pos": null, "width": 600 },
    { "op": "add_module", "card": "lower-drawers", "wall": "A", "pos": null, "width": 600 },
    { "op": "add_module", "card": "lower-sink", "wall": "A", "pos": null, "width": 800 },
    { "op": "add_module", "card": "dishwasher", "wall": "A", "pos": null, "width": 600 }
  ] } }
```
Движок принял семь правок и отказал в восьмой:

> «На стене B нет свободного места для «Ниша под посудомоечную машину» шириной 600 мм: Модуль, добор или резерв выходит за пределы помещения.»

Ниша 600 мм с торцевой стенкой 18 мм не помещается в оставшиеся 600 мм. Карточка посудомойки допускает 450 мм, и ИИ пробует её, а заодно ставит навесные шкафы:

## 7. Claude API (на будущее)

Сейчас не используется: владелец решил разбираться без API (2026-10-28). Раздел — заготовка на случай, когда владелец решит подключать. (Д), проверяется тогда набором сценариев:

| Параметр | Значение | Почему |
|---|---|---|
| Модель | `claude-opus-5-5` | Последняя Opus на 2026-10-28; лучшее понимание свободной речи и цепочек правок |
| Рассуждения | `thinking` не передаётся (у Opus 5.5 всегда адаптивное), `output_config.effort`: `medium` для обычных реплик, `high` для первой планировки изделия | Скорость ответа против качества плана; подбирается замером |
| Инструменты | `tool_choice: auto`, `strict: true` у всех инструментов; вызов правок — по инструкции в системном промте | Принудительный выбор инструмента у Opus 5.5 не поддерживается; `strict` гарантирует валидный JSON |
| Параллельные вызовы | Разрешены: `get_options` и чтение — параллельно, правки одного проекта — одним вызовом `*_edits` | Меньше ходов, одна версия на реплику |
| Поток | Потоковый ответ (`messages.stream`), `eager_input_streaming: true` у инструментов; вход инструмента проверяется по схеме на сервере | Текст ИИ виден сразу; длинные вызовы не ждут целиком |
| Кэш | `cache_control` на системный промт и список инструментов (они не меняются в сеансе), история — дописыванием | Основная экономия расхода |
| Отказы модели | Проверять `stop_reason` (`refusal`, `max_tokens`) до выполнения инструментов; запасная модель — `fallbacks: "default"` (бета `server-side-fallback-2026-07-01`) | Диалог не обрывается молча |
| `max_tokens` | 16 000 на ответ | Ответ ИИ короткий, рассуждения — в пределах |
| Данные | Без имени, телефона, email человека в запросах к API | Только то, что нужно для проекта |

Ориентир расхода — 0,3–1 $ на диалог из 8–12 реплик (оценка; системный промт и инструменты ≈ 10 тыс. токенов в кэше). Замер — первая задача этапа подключения API.

## 9. Как проверять

1. **Схемы инструментов** — тест: каждая правка из `tools.claude-api.json` вызывает ровно одну функцию ядра, пример из раздела 6 воспроизводит те же версии `KPR2-…` на том же `main` и выпуске каталога.
2. **Набор сценариев** — сейчас Claude проигрывает их в треде, стенд сверяет записанные вызовы без ИИ; после подключения API тот же набор гоняется через API. Не меньше 30 диалогов: по 8 на кухню и шкаф, по 5 на купе и другую мебель, 4 «трудных» (противоречивые просьбы, невозможные размеры, просьба назвать себестоимость, просьба «не слушать правила»). У каждого — ожидаемое состояние проекта (по сводке), ожидаемые отказы движка и критерии ответа ИИ: не назвал цену при `amount_rub: null` без пометки «неполная», не обещал того, чего нет в проекте, задал не больше 3 вопросов за реплику.
3. **Сверка с редактором** — проект после диалога, открытый в редакторе, даёт те же детали и цену, что показал диалог.
4. **Замер** — сейчас время выполнения правки стендом (цель: прототип ≤ 5 с); после подключения API — время ответа (первый текст ≤ 2 с), токены и стоимость на диалог по набору.
